# 全局 J 多点重构的实际工作与资源审查

## 1. 已就绪的计算单元

一次昂贵单元是固定有限域和一个 t 点的完整耦合 J 约化与 DE：读取冻结的家族、目标集合和主对象列表；构造这一点的完整 FBI；完成全部目标及主对象导数的 z-IBP；写独立点结果和闭合状态。输入中保留完整低 sector，而非 maximal cut。

同一点内的 FBI 准备与消元关系有实质共享，跨 sector 项不可丢。不同 t 点没有依赖，可在资源允许时全部并行。

执行链为 Python 外层调度→`global_point` C++→共享 FBI 构造器和 `triangular.hpp`。没有 Mathematica、Blade 或 AMFlow 调用。Python 不实现积分约化。

## 2. 真实并发逻辑

`tests/run_reconstruction.py::dispatch` 先把当前已就绪点全部提交到 ThreadPoolExecutor，再按完成顺序处理结果，不按点号或 sector 静态分组。短任务结束后立即领取下一点。`tests/test_dispatch.py` 用真实 dispatch 函数验证容量、恰好执行一次，以及短任务不等待无关长任务。

不同 worker 使用独立点文件和 flock；输入 JSON 和执行二进制复制到唯一 run 目录后使用，避免开发中的源文件改变活跃任务。行为回归验证源输入改动不会改变实际 worker 的冻结输入。

一批点完成后，重构依赖这些点的全部数据。下一批是否需要计算，由当前重构是否通过留出点决定；这个边界来自自适应算法，不是静态分组造成的等待。已验证点保留，恢复时核对 SHA256、返回码、闭合状态及输出哈希。

## 3. 实测成本与拟用资源

本地新鲜 DP 点约 2—3 分钟，单进程单核，观察到的 RSS 约 0.7—1.5 GiB，具体随诊断/缓存及输出模式变化。本地仅使用两个并发点作验证，避免挤占已有桌面负载。

129 点按每点约 150 秒估计约 5.4 CPU 小时；是否足够完成有理重构未知，不能将此估计当成实际取样数。更高阶系数会自适应增加点数。

若远端仍为常见 cp6 的 56 核、约 250000 MiB 节点，一节点动态池比一作业一点更合适。按每点预留 1.5 GiB，56 点并发约 84 GiB，再给整体额外余量；仍须先核实真实节点、软件依赖和已有空闲分配。

Slurm 运行时应由 srun 明确分配、绑定每个单核 worker，并检查实际亲和性。不能直接把本地 `--workers 56` 放进未核实的 batch CPU 访问范围，声称已经有 56 核并发。

## 4. 两类调度浪费的审查

**可避免等待**：各点独立，动态池不会因慢点阻挡其它已就绪点。当前本地测试为资源约束的两个并发，不是每个 sector 串行队列。生产不得按无关 cut 分组排队。

**多个节点同时低利用**：目前拟用一个节点，没有将每点拆成独占节点作业的依据。即使需要更多点，优先同节点动态领取，完成后统一释放，避免收尾时多个节点各剩少量进程。

这份审查不等于已申请资源。SSH 连续超时，尚未核实远端当前节点/分配、FLINT 编译环境及部署。未生成通过机械预检的生产提交凭证，也未调用 sbatch。恢复连接后必须按 tianhe-slurm 技能完成依赖检查、实际执行复审、prepare 和受控 submit，不能跳过这些步骤。
